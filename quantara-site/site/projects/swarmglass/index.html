01 / the question

when an agent meets a strange but plausible information ecosystem, what does it do?

most of what we know about how automated systems read the web comes from what their makers say. quantara's habit is to measure what systems do — model evaluation, failure analysis, behaviour you can reproduce — and swarmglass applies that habit to the reading side of AI: the crawlers, the retrieval pipelines, the tool-using agents that fetch pages on somebody's behalf.

the instrument is a fictional engineering wiki: sixty-odd pages of internally consistent, gently stale documentation for an orchestration platform that never existed, with talk pages, incidents, dead links, an old page index, and attachments. every page can be reached through several doors — an ordinary link, a comment in the html, a line in robots.txt, a sitemap entry, a feed item, a json-ld field, a Link: header, a tool manifest — and which door a visitor uses is the first thing we learn.

we want to know: what do they read, in what order, how deep; which machine-readable affordances they follow and which they ignore; whether they respect robots.txt after reading it; what they remember and repeat; whether information moves between apparently separate sessions; and whether coordination between visitors can be seen at all from passive, privacy-conscious telemetry.

02 / how it works

a website that keeps notes, and nothing else.

swarmglass never fetches, never calls back, never instructs. it serves pages and records the requests.

fig. 01 — one request, start to finish

fig. 01 — the arrows only point one way. the visitor gets a page; we get a line in a table; the world gets aggregate findings.

i.

fifteen doors

every page has a known discoverability class: visible link, html comment only, robots-only, sitemap-only, feed-only, json-ld-only, opengraph-only, header-only, manifest-only, api-only, index-only, orphan… reaching a page tells us which list the visitor read.

ii.

inert canaries

every response carries identifiers like the one below, in six placements — visible text, an html comment, a meta tag, json-ld, a header, the alternates. when one comes back in a later request we learn what was read, and whether it crossed sessions.

iii.

one variable at a time

experiments change exactly one thing for a deterministic subset of visitors — where a link is, what a title says, whether json-ld is present, how deep a page sits — and compare outcomes across arms with intervals.

iv.

legible heuristics

traits and likely classes come from a plain json file of rules with weights. every label ships with the rules that fired and the margin over the runner-up. user-agent strings are treated as claims.

v.

a story view

the private console reconstructs what a session did step by step — read robots.txt first; fetched a disallowed path 4s later; presented a canary it was shown in an html comment — without asserting who or what did it.

vi.

synthetic control traffic

nine caricature personas exercise the whole pipeline and are tagged so test data can never be mistaken for observation. the calibration matrix is the first published finding.

03 / found a canary?

if you are here because you saw one of these strings somewhere, this is what it is.

QUANTARA-SWARMGLASS-R7-4F91C2

an archive reference planted on the mirror. R7 says it was route-scoped (the same for every visitor of page 7); an S would mean it was issued to one session only. the six hex characters are a keyed hash and carry no information without the instance that issued them. the string does nothing. it is not a token, a key, a tracking pixel or an instruction.

if it turned up in a search index, a forum post, a dataset, or a model's answer, that is exactly the kind of propagation swarmglass studies, and we would like to know. write to the contact in the mirror's /.well-known/security.txt.

04 / how to read the numbers

observed behaviour on one side of the line, speculation on the other.

swarmglass produces statements about requests: what was asked for, in what order, with what headers, at what pace. from those it derives heuristic labels — search-bot-like, retrieval-agent-like, naive-crawler-like — that are behavioural categories with the rules that fired attached. it does not, and cannot, say which model, company or person was behind a session.

published findings keep that line. “sessions whose declared user-agent contained X read robots.txt first 80% of the time” is a finding. “a canary shown only in an html comment came back from a different network forty minutes later” is a finding — the strongest kind we make. “model Y reads html comments” is not, and will not appear here.

05 / the refusals, applied

passive means passive.

01

no hack-back

no probing, scanning, fingerprinting beyond coarse aggregates, exploiting, or contacting any visitor. there is no outbound connection in the code.

02

no injection

no page contains an instruction addressed to a visiting model. agent-flavoured titles are titles; the bodies are operator runbooks for fictional humans.

03

no secrets as bait

no credentials, keys, payloads or exploit text, real or fake. the “tools” in the manifests are read-only fetches of the same host.

04

no third parties

no real organisation, product, host, model or person in the fiction. documentation-reserved addresses that cannot route.

05

no individuals

addresses truncated and hashed with a salt that rotates daily; headers allowlisted; bodies never stored; ninety days and gone. public exports go through a sanitizer that refuses anything address-shaped.

06

no deception about who runs it

the mirror's about page, privacy policy, disclaimer, humans.txt and security.txt name the operator and the purpose. the fiction is styling.

06 / reproduce it

the pipeline is public; the observations are ours.

anyone can run the instrument and check that it does what this page says. the telemetry from the live mirror stays on the box.

git clone https://github.com/Metrix187/swarmglass && cd swarmglass
npm install && npm run dev            # mirror :8080 · console :8081
npm run synth -- --personas all      # nine personas, tagged as synthetic
npm test                              # 40 end-to-end and unit tests

then open the console's synthetic view: each persona should land in the class it was written for. that matrix is F-000, the first finding, and it is a self-consistency check rather than an observation of the world. every later finding names its experiment id, seed version, heuristics version and window, and ships a bundle with a checksum. the repository's docs/REPRODUCIBILITY.md walks through regenerating a published table.

experiments live in config/experiments/, one variable each. seven run at launch: discovery channel, structured data, title style, link depth, representation preference, deprecation flag, documentation language. the fictional element behind each stimulus is listed in docs/FICTION_MAP.md, so nothing on the mirror needs a research label.
